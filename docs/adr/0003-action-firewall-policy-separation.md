# ADR-0003: Action Firewall and Policy Separation

- **Status**: Accepted
- **Date**: 2026-11-12
- **Deciders**: ATLAS Core Architecture Team
- **Technical Story**: Phase 1 Foundation

---

## Context and Problem Statement

Autonomous computer-use models translate user objectives into concrete machine actions: clicking screen coordinates, dispatching keystrokes, writing files, executing shell commands, or navigating browser sessions.

Because generative models operate probabilistically, they are susceptible to hallucinations, prompt injections, and adversarial manipulations. A model may attempt to:
- Overwrite or delete sensitive operating system or user files.
- Execute unauthorized network exfiltration or submit sensitive credentials.
- Perform destructive or irreversible transactions (e.g., billing authorizations, database drops).

If low-level execution drivers directly accept model outputs without an intermediate governance boundary, catastrophic failures cannot be reliably prevented.

The central design axiom of ATLAS states:

> **The model makes decisions. ATLAS controls execution.**

We need a dedicated, decoupled policy layer that intercepts and evaluates every proposed action before it reaches any operating system or browser driver.

---

## Decision Drivers

- **Zero Trust Execution**: No action proposed by a model or external worker is assumed to be safe.
- **Human-in-the-Loop Gating**: Sensitive operations must be able to pause execution and solicit human approval before proceeding.
- **Separation of Concerns**: Drivers must remain dumb execution mechanisms; models must focus on reasoning; policy enforcement must reside in a dedicated domain package.
- **Auditability**: Every authorization decision (approval, rejection, dry-run simulation) must be recorded in the event store.

---

## Considered Options

1. **Option A: Model Self-Moderation via System Prompts** (relying on prompt instructions to avoid dangerous actions).
2. **Option B: Ad-Hoc Validation Inside Drivers** (placing `if/else` checks inside browser and OS driver implementations).
3. **Option C: Centralized Action Firewall and Policy Package (`packages/atlas-policy`)**.

---

## Decision Outcome

**Chosen Option: Option C (Centralized Action Firewall and Policy Package)**.

All action requests generated by any planner or model must pass through `packages/atlas-policy` prior to driver dispatch.

```
Model Proposal (ComputerAction)
             │
             ▼
[Action Firewall (atlas-policy)]
  ├── 1. Schema Validation (valid action_type, target, parameters)
  ├── 2. Target & Parameter Sanitization
  └── 3. Policy Rule Evaluation
             │
   ┌─────────┼───────────────────┬──────────────┐
   ▼         ▼                   ▼              ▼
[ALLOW]  [REQUIRE_APPROVAL]    [BLOCK]      [DRY_RUN]
   │         │                   │              │
Dispatch   Transition Task to  Raise Policy   Record simulated
to Driver  WAITING_APPROVAL    Violation &    result; do not
           & await human auth  Transition to  call driver
                               FAILED
```

### Policy Evaluation Categories

1. **`ALLOW`**: Safe, non-destructive, or read-only actions (e.g., capturing a screenshot, reading the accessibility tree, querying active window titles). Dispatched immediately to the driver.
2. **`REQUIRE_APPROVAL`**: Sensitive actions that alter persistent state or incur external impact (e.g., file writes, sending HTTP POST requests, clicking payment or delete buttons). The state machine transitions the task to `WAITING_APPROVAL` and emits a notification event.
3. **`BLOCK`**: Explicitly forbidden operations (e.g., modifying system registry, formatting drives, executing shell commands containing privilege escalation patterns). The firewall rejects the action, logs an audit violation, and halts task execution.
4. **`DRY_RUN`**: Simulates action execution without invoking hardware or OS drivers, useful for testing, verification, and offline safety audits.

---

## Consequences

### Positive
- **Guaranteed Enforcement**: Execution drivers never execute unauthorized actions; bypassing the firewall is architecturally impossible.
- **Configurable Risk Profiles**: Policy rule sets can be configured based on task priority, environment (sandbox vs production), and user preferences.
- **Human Oversight**: Provides deterministic hooks for interactive human approval workflows.
- **Audit Defense**: Creates an evidentiary record proving that every executed action satisfied compliance rules.

### Negative / Risks
- **Evaluation Latency**: Introduces a minor evaluation step in the execution pipeline (target latency: < 2ms for local rule matching).
- **Policy Maintenance**: Requires maintaining comprehensive, well-tested rule sets to prevent false rejections of benign actions.

---

## Compliance & Verification

- `tests/unit/test_policy_firewall.py` verifies rule evaluation across `ALLOW`, `REQUIRE_APPROVAL`, `BLOCK`, and `DRY_RUN`.
- Integration tests confirm that attempting to bypass the firewall or dispatching blocked actions halts execution and records a policy violation event.
